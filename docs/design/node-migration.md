# Сервер на Node: новая архитектура и переключение

План (01.11.2026). Сервис на Python (`service/`: FastAPI + SQLModel + Alembic) заменяется новым сервисом на TypeScript/Node, спроектированным заново. Переходного периода с двумя стеками нет: старый работает как есть, пока новый собирается и проверяется рядом; затем одно переключение — остановка, перенос данных скриптом, запуск. Реальных пользователей нет, простой допустим; данные одного пользователя (рецепты с фото, партии с журналом, оборудование) переносятся — это дёшево и страхует.

Код и тесты Python — **спецификация** (что сервис умеет, крайние случаи, тексты ошибок), не шаблон для копирования. Агент (`agent/`) остаётся на Python; протокол на проводе не меняется — одно уточнение смысла `ack`, см. «Реальное время».

## Что получаем

- Один язык: расчёты, программа пивоварни, пересчёт под оборудование, расписание брожения — один пакет `core` для браузера и сервера; четыре пары «близнецов» и `shared/update.py` исчезают, 3700 строк общих примеров становятся обычными тестами.
- Сервис, построенный под своё сердце — хаб агентов, поток SSE и фоновые напоминания — на зрелых библиотеках Node, а не на экспериментальных возможностях Nitro.
- Схему базы и границы модулей можно исправить сразу: теперь это дешевле, чем когда-либо потом.

## Решения

### 1. Где живёт API — отдельное приложение, не Nitro

**Рекомендация: `apps/api` — Fastify 5**, рядом с ним `apps/web` — Nuxt только для интерфейса и SSR. Контейнеров два, как сейчас (`api` на 8000, `web` на 3000), **nginx не меняется** — `/api/agent`, `/api/stream`, `/api/` уже идут на 8000.

Почему не внутри Nuxt (Nitro): WebSocket в Nitro 2.13 (`nitropack 2.13.5`, `crossws 0.3.5` в `web/package-lock.json`) — экспериментальный; фоновые задачи (`scheduledTasks`) — тоже; SSR, API, WS и обработка фото делили бы один цикл событий; `nuxt dev` перезапускает сервер при правках и роняет агентов. Выигрыш Nitro — минус один контейнер (~100 МБ) и вызовы API при SSR без сети — не стоит того, чтобы ядро сервиса жило на эксперименте. SSR-страницы ходят в `api` по сети compose, как сейчас (`NUXT_API_SERVER`).

Fastify против Hono:

| | Fastify 5 | Hono |
|---|---|---|
| WebSocket | `@fastify/websocket` поверх `ws` — зрелый, доступ к заголовкам при upgrade, отказ до открытия (403 — нужен агенту) | `@hono/node-ws` поверх `ws` — моложе, тоньше |
| SSE | `reply.raw` потоком (10 строк) или `fastify-sse-v2` | `streamSSE` встроен — удобнее |
| Тело-картинка | `addContentTypeParser('image/*', {parseAs:'buffer', bodyLimit})` — лимит тела встроен | `c.req.arrayBuffer()`, лимит — middleware `bodyLimit` |
| Лимиты попыток | `@fastify/rate-limit` (по адресу) + свои счётчики по почте | `hono-rate-limiter` |
| Валидация и OpenAPI | zod через `fastify-type-provider-zod`, `/docs` даром через `@fastify/swagger` | zod встроен, `@hono/zod-openapi` |
| Тесты | `app.inject()` — HTTP без сети, быстро | `app.request()` — то же |
| Структура | плагины с инкапсуляцией — раздел = плагин, зависимости через `decorate` | middleware и группы маршрутов |
| Остановка, журнал | `close` с хуками, pino встроен | своими руками |
| Память | ~40 МБ пустой | ~30 МБ |

Выбор — Fastify: лучше покрывает именно то, что у нас сложное (WebSocket с отказом до upgrade, лимит тела у сырых картинок, аккуратная остановка), и тестируется без сети. Hono легче и приятнее в коде, но выигрывает там, где нам не надо (edge-runtime). Альтернатива остаётся рабочей — разница в объёме кода невелика.

### 2. Монорепа — pnpm workspaces, без turbo

```
hoplab/
  package.json, pnpm-workspace.yaml, tsconfig.base.json, eslint.config.mjs
  packages/core/      чистый TS, без зависимостей кроме zod: рецепт (схема и типы), показатели, программа
                      пивоварни, пересчёт под оборудование, расписание брожения, шаги варочного дня, вода
  apps/api/           Fastify: разделы, база (Drizzle), хаб, SSE, напоминания, push, почта, CLI
  apps/web/           Nuxt (нынешний web/ как есть, минус близнецы; прокси /api остаётся — через него SSR и dev)
  agent/              Python — без изменений, вне workspace; свой CI-job
  deploy/, docs/
```

- **pnpm workspaces** — достаточно: два приложения и один пакет, один разработчик. `pnpm -r run test` запускает всё; turbo (кэш и граф задач) — когда сборка станет ощутимо долгой, добавить несложно.
- **`core`** — то, что сейчас раздвоено (`calc`, `program`/`recipe`, `scale`, `reminders`/`brewlog`) плюс `brewday.ts` (шаги дня), `water.ts`, схема `Recipe` на zod (сейчас `recipes/schemas.py` и типы из OpenAPI). Никаких импортов из Nuxt или Fastify; собирается в ESM, `apps/web` и `apps/api` импортируют исходники через workspace.
- **`db` — не отдельный пакет, а `apps/api/src/db`.** Потребитель один (API и его CLI, включая скрипт переноса); пакет появится, если появится второй.
- **`contracts` — не пакет.** Схемы тел и ответов живут рядом с маршрутами раздела (`apps/api/src/recipes/schemas.ts`), из них Fastify строит OpenAPI. Интерфейсу типы приходят как сейчас — `openapi.json` → `nuxt-open-fetch` → `$api`/`useApi`: код интерфейса не меняется, клиент не самодельный, API задокументирован. Генератор — `pnpm --filter api openapi` (вместо `python -m app openapi`), CI сверяет файл. Альтернатива — пакет `contracts` с zod и типизированный клиент поверх `$fetch` (без генерации и файла; ценой своего клиента ~100 строк и правки всех вызовов `useApi`) — если захочется уйти от OpenAPI, это делается потом и локально.
- Протокол агента — zod-схемы сообщений в `apps/api/src/brewery/protocol.ts`; описание по-прежнему `agent/README.md`.

### 3. Слои внутри API

```
apps/api/src/
  app.ts            buildApp(deps): плагины, разделы, ошибки → {detail}, Origin, cookie, OpenAPI
  main.ts           настройки (zod из env), база и миграции, deps, старт, остановка
  config.ts · errors.ts · access.ts · auth/session.ts (request.viewer)
  db/               schema.ts (Drizzle), client.ts, migrations/ (drizzle-kit)
  auth/     recipes/     discussion/     notifications/     push/     equipment/     brews/     brewery/
    routes.ts        HTTP: схема запроса, кто спрашивает, вызов сервиса, код ответа
    service.ts       смысл: права (access.ts), правила, ошибки предметной области
    queries.ts       SQL на Drizzle — функции, не классы; транзакции — здесь
    schemas.ts       zod: тела и ответы → OpenAPI
  brewery/           hub.ts (WebSocket, соединения, снимки), protocol.ts, control.ts (команды),
                     journal.ts (записи от агентов), devices.ts, agents.ts, streams.ts (SSE)
  brews/             logbook (партии, записи, фазы), brewday (шаги, таймеры), reminders (брожение), scheduler.ts
  mail.ts · push/sender.ts · photos.ts (sharp) · throttle.ts
  cli/               agents new|list · vapid · openapi · import-legacy (перенос данных)
```

- **Маршрут** не знает SQL, **сервис** не знает HTTP, **queries** не знают прав. Как в Python сейчас: ошибка предметной области (`Invalid 400`, `Forbidden 403`, `NotFound 404`, `Conflict 409`, `Unsupported 415`, `Offline 503`…) бросается в сервисе, общий обработчик делает `{detail}`; 422 — список по полям от zod. Тексты ошибок — из Python, они уже для человека.
- **Кто спрашивает** — хук `onRequest`: cookie `hoplab_session` → `request.viewer` (гость или пользователь), продление сессии и cookie раз в час; `requireUser`, `requireAdmin` — хуки маршрута. **Права — только `access.ts`** (`access.py` как спецификация: чужие личные рецепты не видит никто, модерация — опубликованных, публикация — с подтверждённой почтой).
- **Зависимости** (`hub`, `streams`, `pusher`, `mailer`, `scheduler`, `db`) — `buildApp(deps)` и `fastify.decorate`: глобального состояния нет, тесты собирают приложение с подменами (письма в ящик, push в список), как `service/tests/support.py` сейчас.
- **Раздел = плагин Fastify** с префиксом; разделы не импортируют `queries` друг друга — только сервисы (обсуждение зовёт `notifications.service`, журнал пивоварни — `brews.service`, `equipment.service`).

### 3а. Правила для агентов и проверка архитектуры

Архитектура держится не на памяти и не на прозе: правила задают направление, линтер и CI не дают свернуть, ревью ловит остальное. Делается на шаге 0, до первого раздела.

- **Правила в одном месте** — раздел «Архитектура API» в `CLAUDE.md` репозитория (`AGENTS.md` ссылается на него — Claude и Codex читают одно): слои, из чего модуль, куда что класть, запреты, как добавить раздел. Коротко, с путями, без пересказа этого плана.
- **Эталонный модуль и шаблон** — на шаге 0 структуру показывает `health` (маршруты, сервис, схемы, публичный `index.ts`; базы ещё нет). Первый раздел с базой — «оборудование» (шаг 3, сразу после входа): маршруты, сервис, queries, схемы, тесты целиком по правилам; из него — шаблон `pnpm new:module <имя>`, с которого начинаются остальные разделы. По живому примеру агенты пишут точнее, чем по описанию, а шаблон без базы до шага 3 не проверялся бы компиляцией.
- **Границы — линтером** (ESLint, `eslint-plugin-boundaries` или `import/no-restricted-paths`; при нужде — `dependency-cruiser`), ошибкой, а не предупреждением:
  - `packages/core` не импортирует ничего из `apps/*`, Drizzle, Fastify, Node-API — чистый TS для сервера и браузера;
  - в разделе Drizzle и SQL — только в `queries.ts`; `routes.ts` не зовёт `queries.ts` напрямую, только `service.ts`; `service.ts` не знает `request`/`reply`;
  - разделы видят друг друга только через `index.ts` (публичный сервис), не через внутренние файлы;
  - права — только через `access.ts`; `process.env` — только в `config.ts`; глобальные синглтоны запрещены (зависимости — через `buildApp(deps)`);
  - `apps/web` не импортирует `apps/api` — только `core` и сгенерированные типы.
- **Типы — строго:** `strict`, `noUncheckedIndexedAccess` у `core` и `api`; `any` — только с комментарием-обоснованием (правило линтера). Project references не нужны: `core` подключается исходниками, каждый пакет проверяется своим `tsc --noEmit` (web — `nuxt typecheck`).
- **CI** — `pnpm lint`, `pnpm typecheck`, тесты всех пакетов, сверка `openapi.json`: нарушил границу — не собирается и не выкатывается.
- **Ревью** — проверяет то, что линтер не видит: права в `access.ts`, ошибки предметной области в одном формате, тесты у раздела, транзакции там, где пишется несколько таблиц; чек-лист — в том же разделе `CLAUDE.md`.
- **Остальные страховки — тоже автоматом:**
  - **форматирование** — ESLint stylistic, как сейчас в `web/` (без отдельного Prettier): одно правило на весь монорепо, `pnpm lint --fix`;
  - **покрытие** — у `packages/core` порог (≈ 90 % строк: это расчёты, ошибка в них — неверный рецепт), у API — не ниже текущего по разделам;
  - **тесты как документация** — у каждого раздела тесты по сценариям из `docs/scenarios.md`; общие примеры `shared/` становятся тестами `core`;
  - **зависимости** — `pnpm audit --audit-level high` отдельным job: красная отметка в PR, но выкатку не держит (уязвимость в чужой зависимости не должна стопорить срочную правку);
  - **мёртвый код** — `knip` в CI для `packages/core` и `apps/api`: неиспользуемые файлы, экспорты и зависимости — агенты оставляют их чаще людей. У `apps/web` не включаем: автоимпорты Nuxt дают ложные срабатывания, которые агент начнёт «чинить»;
  - **секреты** — `gitleaks` в CI отдельным job (тоже вне `build.needs`): репозиторий публичный — ключ или пароль в коммите сразу виден в PR;
  - **схема базы** — миграции только генерируются (`drizzle-kit generate`) и проверяются в CI на пустой базе и на копии с данными; руками SQL в миграции — только с комментарием-обоснованием;
  - **контракт API** — сверка `openapi.json` в CI (как сейчас): поменял ответ — обнови схему и интерфейс в том же коммите;
  - **протокол агента** — схемы сообщений в zod рядом с хабом и тест «агент на Python ↔ хаб на Node» в CI: изменение с одной стороны без другой не пройдёт.
- **После переключения, отдельным решением** — то, что на одного разработчика во время переноса даёт больше настройки, чем пользы: Renovate или Dependabot (обновления маленькими PR), `lint-staged` + husky перед коммитом, `@fastify/under-pressure`.

### 3б. Библиотеки сверх основных

Проверено по npm 01.11.2026; версии закреплять точно.

| Что | Когда | Зачем |
|---|---|---|
| Drizzle **1.0** (сейчас `1.0.0-rc.5`, стабильная — 0.45) | шаг 2 — сразу на 1.0, версия закреплена точно | у 1.0 другой формат папки миграций и новые запросы по связям; начать на 0.45 — значит переезжать второй раз, уже с данными. Источник истины — сгенерированный SQL миграций: если RC подведёт, откат на 0.45 дешёвый |
| `close-with-grace` | шаг 0 | SIGTERM от `docker stop` → `app.close()` (раздел 5) с таймаутом: зависшее закрытие не держит контейнер |
| `@fastify/under-pressure` | после переключения | `/api/health` показывает задержку цикла событий и память; при перегрузке API отвечает 503, а не копит запросы до `mem_limit` |
| `@hey-api/openapi-ts` + клиент Nuxt + плагин `@pinia/colada` | после переключения, отдельным шагом | вызовы API — функциями (`getRecipe({ path: { rid } })`), а не строками адресов; запросы с ключами кэша: поток SSE сбрасывает кэш по ключу (новое уведомление → список уведомлений) вместо ручных `refresh()`. Не в перенос: это правка всех 81 вызова API в 30 файлах интерфейса; hey-api ещё до 1.0 (0.99, бывают выпуски с 15 ломающими изменениями, документация просит закреплять версию), клиент Nuxt — бета. После переключения контракт тот же, переход ничего не ломает. Pinia Colada — 1.4, от автора Pinia, есть модуль Nuxt |

Не берём:
- **проверку ответов zod в браузере** (плагин hey-api) — оба конца наши, контракт сверяет CI;
- **`@hey-api/transformers`** (даты → `Date`) — в контракте unix-секунды;
- **SSE-клиент hey-api** — `EventSource` сам переподключается и шлёт cookie;
- **плагин `fastify` у hey-api** — он для порядка «сначала спецификация, потом сервер», у нас наоборот;
- **`drizzle-zod` для схем API** — контракт (camelCase, unix-секунды, без служебных колонок) не выводится из таблиц, иначе схема базы протекает в API;
- **`@fastify/helmet`** — заголовки безопасности — задача nginx: одно место для страниц и API.

### 4. Схема базы — заново

Что оставить из нынешней (`models.py`, [data.md](../data.md)): UUID-ключи, `timestamptz`, рецепт одним JSONB-документом (решение из [decisions.md](../decisions.md) в силе), фото в базе, каскады, частичный уникальный индекс «одна основная система», `name_key` для ников, хэши токенов. Что изменить:

| Было | Станет | Зачем |
|---|---|---|
| `users.avatar` bytea в строке пользователя | таблица `user_avatars (user_id, data)`; `avatar_version` остаётся в `users` (по нему профиль и список рецептов строят адрес аватара и понимают, есть ли он) | пользователь читается всюду — байты аватара не должны ехать с ним |
| `recipes.data` без версии формата | `recipes.doc` JSONB + `doc_version` smallint | формат растёт (вода, брожение); миграция документов — по номеру, а не по догадкам |
| `brews.recipe` (программа как в пивоварне), `snapshot`, `plan`, `reminded` — четыре JSONB | `brews.program` (nullable; у ручных партий сейчас `{}` → NULL), `brews.batch_recipe`, `brews.plan`; `reminded` → таблица `brew_reminders (brew_id, key, sent_at, silent)`, уникальный `(brew_id, key)`; `sent_at` и `silent` у перенесённых строк — NULL (в `reminded` были одни ключи), новые строки планировщик заполняет всегда | имена по смыслу. `reminded` — **журнал уже отработанных ключей, а не очередь**: что пора напомнить, пересчитывается на каждом проходе из плана, записей журнала и текущего времени (`reminders.py`); ключи `measure-…`, `stuck-N`, `stable-N`, `dry-gN` появляются только после замеров, поэтому сроков в таблице нет |
| `brews.status` + `day_ended_at` + `source` + фазы, вычисляемые на лету | то же, но `phase` считается в `core` одной функцией и для списка, и для страницы; `source` остаётся | фаза — одно правило; `source` не выводится из `device_id`: у устройства `ON DELETE SET NULL`, и удаление пивоварни переписало бы историю партий |
| `readings` без срока | `readings` + задача прореживания: старше 30 дней — одна точка в минуту; `temp`, `target` — `real` | 2 с × варка = ~15 000 строк за день; за год у активного пивовара — миллионы; графику варки месячной давности поминутно достаточно |
| `events.data` JSONB с чем попало | `events.data` JSONB по zod-схеме из протокола | валидируется на входе от агента |
| `notifications.data` только у напоминаний | `data` у новых уведомлений всех видов (снимок для push), `kind` с check-ограничением; у перенесённых без данных (комментарии, ответы, напоминание с `data = null`) — `{}`, текст не выдумывается; лента комментариев и ответов, как в Python (`feed.py`), строится живьём через join с `comments` и `recipes` | один формат для интерфейса; правка комментария и переименование рецепта видны в ленте |
| строковые перечисления без ограничений | `text` + `check (… in (…))`. Исключения без check: `equipment.kind` — каталог видов живёт в коде, убранный из каталога вид остаётся у старых записей и показывается как «Другое»; `events.kind` и `readings.status` — словарь протокола агента, его расширение не должно требовать миграции | честная схема, миграции проще, чем с типами enum |
| `sessions` без чистки | `sessions` + ночная чистка истёкших (`operations.md` «чистки пока нет») | таблица не растёт вечно |

Ключи — UUID v7 у таблиц, где сейчас UUID (`uuidv7` из `core`, упорядочены по времени — индексы и сортировки дешевле); старые записи сохраняют свои v4 — ссылки и адреса не ломаются. `events` и `readings` — `bigint identity`, как сейчас.

**Перенос данных** — `apps/api/src/cli/import-legacy.ts`: читает старую базу по `LEGACY_DATABASE_URL` (сырым SQL, без ORM старой схемы), пишет в новую через Drizzle. Порядок — как каскады: `users` → `sessions`, `auth_tokens`, `agents`, `devices`, `equipment`, `recipes` → `recipe_photos`, `favorites`, `recipe_votes`, `comments` → `comment_votes`, `notifications`, `brews` → `brew_entries`, `readings`, `events`, `brew_reminders` (из `reminded`), `push_subscriptions`. Сессии и токены агентов переносятся хэшами, подписки push — как есть: пользователь остаётся вошедшим, агент — с тем же `AGENT_TOKEN`, браузеры — подписанными. Пользователь без почты и пароля допустим (владелец данных в режиме «у себя на ПК», см. «Что легко потерять»). Режимы `--dry-run` (считает и проверяет) и `--verify` (сравнивает таблицы построчно, по всем колонкам). Скрипт — с тестом на дампе старой тестовой базы.

*Уточнено на шаге 2.* Порядок записи — как каскады, но `brews` раньше `notifications` (у напоминаний есть ссылка на партию). `brew_reminders` — составной ключ `(brew_id, key)`; у перенесённых `sent_at` и `silent` — NULL: «перенесено, неизвестно». `notifications.data` у комментариев и ответов, где её не было, — `{}`. Старая база читается страницами по ключу, вставки идут порциями по 500 строк (лимит Postgres — 65 535 параметров на запрос); порядок комментариев (корни, потом ответы) страницы не ломают. Пустая таблица — не ошибка.

**Сверка** (`--verify`, `--verify-only`, `--dry-run`): одним общим механизмом по всем таблицам. Набор колонок берётся из Drizzle-схемы новой таблицы, а не руками; соответствие «колонка → выражение в старой базе» — одноимённая колонка, а где схема изменилась, — явная карта (`recipes.data → doc`, `brews.recipe → program` с `{}` ↔ NULL, `snapshot → batch_recipe`, `users.avatar → user_avatars.data`, `reminded → brew_reminders`, `notifications.data`, `doc_version` — константа 1). Колонка без пары и без записи в карте — ошибка механизма, а не тишина. Обе базы читаются параллельно, страницами по ключу, строки сливаются по ключу — без `string_agg` по таблице и без загрузки её в память. Значения приводятся к общему виду: время — миллисекунды, `readings.temp` и `target` — как `real` (сужение из `double precision` намеренное), остальные числа — `float8`, JSON — по смыслу (`25.0` ≡ `25`; JSON null ≡ SQL NULL), байты — SHA-256, остальное — текстом. Расхождение выдаётся с таблицей, ключом строки и колонкой (не больше 5 примеров на таблицу) и даёт ненулевой код выхода.

**Порядок запуска.** Команду переноса миграции новой базы применяет сама (идемпотентно: папка `drizzle/` есть в образе) и только потом проверяет, что база пуста, — запускать для этого сервис не нужно, он не работает на пустой базе параллельно с переносом. Счётчики identity у `events` и `readings` сдвигаются в самом конце, после успешной сверки и прямо перед commit: при отказе сверки и в `--dry-run` они не тронуты. Время хранится с точностью до миллисекунды (`timestamptz(3)`). Скрипт попадает в образ как `dist/cli/import-legacy.mjs`.

### 5. Реальное время — в процессе, состояние — в базе

- **Хаб агентов** — `@fastify/websocket`: `Map` пивоварня → соединение, снимок, `seq` принятых записей, ожидающие команды. Всё как в `hub.py`: `hello` за 10 с, `welcome`, `ack`, повторы отбрасываются по номеру и запуску агента, при `hello` закрываются варки, о которых агент не знает, кроме `keep`, старое соединение того же агента закрывается, команды не копятся (503 без связи, `AgentLost` при обрыве).
- **Одно уточнение протокола — `ack` после записи в базу.** Сейчас `ack` уходит после постановки в очередь журнала; при переполнении очереди записи теряются «с предупреждением», хотя уже подтверждены. В новом хабе сообщение агента обрабатывается и записывается, `ack` — после commit. На проводе ничего не меняется, агент (`link.py`) ничего не замечает; «записи не теряются» становится правдой. Показания температуры (раз в 2 с) — пачкой раз в секунду, одним `insert`. **Инвариант порядка:** агент по `ack(seq)` выбрасывает всё с номером ≤ seq (`link.py`), поэтому сообщения одного соединения пишутся строго по порядку `seq`: перед записью любого другого сообщения пачка показаний сбрасывается, `ack` уходит, только когда в базе всё ≤ seq. Тест: событие между двумя показаниями, обрыв — ничего не потеряно (продолжение `test_hung_service_loses_nothing`).
- **Поток SSE** — реестр подписчиков по пользователю в памяти (`streams.ts`), пинг раз в 15 с, `X-Accel-Buffering: no`. Публикуют хаб (`state`, `event`), журнал (`brew`), планировщик и обсуждение (`notice`). Очередь (Redis и т. п.) **не нужна**: один процесс, один сервер, пользователей единицы; горизонтальное масштабирование — не в этом плане.
- **Фоновые задачи** — `scheduler.ts` в процессе, устроен как сейчас (`ticker.py`), а не как очередь со сроками: напоминания о брожении — проход раз в 5 мин, `core` пересчитывает «что пора» из плана, записей журнала и `now`, отработанное отмечается в `brew_reminders`; таймеры варочного дня (конец шага, 36 ч на закрытие дня) — ближайший срок считается в памяти по идущим дням. Опоздание больше 12 ч — молча помечается (`decisions.md`). Состояние задач — только в базе, поэтому **перезапуск ничего не теряет**: на старте планировщик пересчитывает сроки, хаб ждёт агентов (они переподключаются сами и досылают неподтверждённое), вкладки переподключаются к SSE (`retry: 2000`) и получают свежий `state`.
- **Остановка** — `app.close()`: WS агентам закрывается кодом 1001, SSE — обрывом, журнал дописывает очередь, затем закрывается пул базы. Docker `stop_grace_period: 15s`.
- Push (`web-push`) и письма (nodemailer) — очереди в памяти с ограничением; потеря при падении — как сейчас, допустимо.
- **Шов на будущее вместо Redis сейчас.** Публикация событий (SSE) и фоновые задачи — за двумя маленькими интерфейсами в `apps/api`: `EventBus` (опубликовать / подписаться) и `Jobs` (запланировать / выполнить). Сейчас обе реализации — в процессе. Понадобится второй экземпляр API или надёжная очередь с повторами — подставляется реализация на Postgres (`LISTEN/NOTIFY`, `pg-boss` / `SKIP LOCKED`) или на Redis, без переписывания разделов. До тех пор Redis — лишний контейнер и память без пользы.

### 6. Вход — совместимость без сброса пароля

Из `auth/passwords.py` и `auth/sessions.py` воспроизводится байт в байт стандартной `node:crypto`:
- пароли: `scrypt`, N = 16384, r = 8, p = 1, dklen 32; строка `scrypt$N$r$p$соль$ключ`, base64url без `=`; `crypto.scrypt` с теми же параметрами (`maxmem` по умолчанию 32 МБ ≥ 128·N·r = 16 МБ), `timingSafeEqual`; пустышка-хэш для несуществующей почты — остаётся (время ответа одинаковое);
- сессии: 32 случайных байта base64url, в базе SHA-256 hex; cookie `hoplab_session` httpOnly, `SameSite=Lax`, `Secure` при https (по `X-Forwarded-Proto` от nginx), `path=/`, 30 дней, продление не чаще раза в час;
- ссылки из писем: тот же токен, SHA-256, сроки 2 дня / 1 час, одноразовые;
- токены агентов: SHA-256 hex — агент работает без нового токена.

Тест «хэш и токен, выданные Python, принимаются» — строки из старой тестовой базы в фикстуре. Лимиты попыток: по адресу — `@fastify/rate-limit`, по почте и на комментарии — свой счётчик в памяти (как `throttle.py`; перезапуск сбрасывает — так задокументировано). Проверка `Origin` у изменяющих запросов — хук `onRequest`.

### 8. CI и выкатка

- **Ветка `node` до переключения.** Пуш в `main` — выкатка на прод, а уже шаг 0 переносит `web/` в `apps/web` и меняет `deploy.yml`, шаг 7 переводит интерфейс на новый API. Поэтому вся работа — в долгой ветке `node`, шаги — PR в неё: CI на `pull_request` проверяет, `build` и `deploy` идут только с `main`. В `main` на это время — только срочные исправления старого стека, каждое сразу вливается в `node`. Слияние `node` → `main` и есть переключение (шаг 8).
- **CI в ветке `node`:** job `service` (pytest старого сервиса и сверка `openapi.json`, сгенерированного из Python — как сейчас) живёт до шага 7: до него интерфейс получает типы из старого API. Job `agent` (ruff, pytest — как сейчас). Job `node` (pnpm, lint, typecheck, тесты `core`, `api` с сервисом Postgres и Python 3.13 для дымовых тестов хаба, `web`). На шаге 7 сверку `openapi.json` забирает `pnpm --filter api openapi`, job `service` уходит вместе с `service/` на шаге 8.
- **Build и deploy** — образы `ghcr.io/sansay90/hoplab-api` (вместо `hoplab`) и `hoplab-web` (Dockerfile'ы в `apps/*`, контекст — корень репозитория из-за workspace); в `deploy.yml` сервис compose и образ переименовываются (`pull app web` → `pull api web`).
- **Compose:** `db` (новый том `pgdata2`), `api` (8000, `env_file: .env`, `DATABASE_URL`, **HEALTHCHECK** по `/api/health` — `web` ждёт `service_healthy`), `web` (3000, `NUXT_API_SERVER=http://api:8000`). **nginx — без правок.** Fastify — с `trustProxy`: nginx шлёт `X-Forwarded-For/Proto`, без этого лимиты по адресу увидят адрес nginx, а cookie не получит `Secure`.
- **Проверка перед переключением — на ПК** (решение 5): восстановленный `pg_dump` прода + `import-legacy`, проверка руками в браузере и настоящим агентом (у агента временно `SERVICE_URL` на ПК). Стенда на сервере нет: на сервере — сразу переключение, откат — старый compose и том.
- **Переключение** (окно ~30 мин, пошагово в `operations.md`): `docker compose stop app web` → `pg_dump` старой базы → новый `compose.yaml` в `/opt/hoplab` → перенос `docker compose run --rm api node dist/cli/import-legacy.mjs --verify` (сам применяет миграции в новой базе, затем переносит и сверяет; поднимается только `db` как зависимость, `api` и `web` ещё не запущены) → `up -d` нового стека → агент переподключается (тот же токен и адрес) → проверка: вход, рецепты, фото, партия, SSE, команда пивоварне. Старые контейнеры и том `hoplab_pgdata` **не удаляются месяц**.
- **Откат:** вернуть старый `compose.yaml`, `up -d app web` — nginx не трогался, том старой базы цел. Данные, записанные в новый стек после переключения, при откате теряются — поэтому первые дни после переключения не варить.

## Что легко потерять при переносе

То, что делает нынешний сервис, но не видно из названий разделов. Каждый пункт — в тестах своего шага.

- **Режим «у себя на ПК»** (шаг 3): без `APP_URL` доверенный адрес — локальный (`LOCAL_ORIGIN`), первый зарегистрировавшийся — администратор, «владелец данных до входа» — пользователь без почты (`auth/users.py`, `config.py`, `test_auth.py`). Адрес сайта в письмах — из `APP_URL`, без него ссылка из письма — 500 (`auth/router.py`).
- **CORS** (шаг 0): как сейчас — только доверенный адрес, с cookie (`@fastify/cors`); нужен, если интерфейс ходит в API по `NUXT_PUBLIC_API_BASE` с другого адреса.
- **Фото** (шаг 4): больше 10 МБ — 413 ещё при чтении тела, автор снимка (`credit`) в query, `Cache-Control: private, immutable`, `X-Content-Type-Options` (`recipes/router.py`); аватар — 256 px с обрезкой по центру, как `ImageOps.fit` (`auth/profile.py`, шаг 3).
- **Каталог видов оборудования** (`GET /equipment/kinds`, `brewery/kinds.py`): данные и правила — в `core` на шаге 1 (интерфейс считает по ним свойства), API отдаёт на шаге 3 вместе с оборудованием.
- **Push от событий пивоварни** (шаг 6): тревоги (`ALERTS`, `urgent`), кнопки-действия с адресами `/api/alert/confirm` и `/api/additions/{m}/ack`, «нет связи» и «пивоварня выключена» — только во время варки (`push/pusher.py`).
- **Владелец пивоварни** (шаг 6): `hub.owner()` пустой, пока агент не подключился после запуска сервиса — от этого зависит, кому идут SSE и push (`hub.py`, `main.py`); поведение сохранить и покрыть тестом.
- **Формат чисел в тексте сухого охмеления** (шаг 5): `dryHopDays` в `core` пишет количество через `toLocaleString('ru-RU', { maximumFractionDigits: 1 })`, Python (`logbook.py`, `dry_hops_of` и `ru_num`) — через `%g`: 75,25 даёт «75,3» против «75,25», 1000 — «1 000» против «1000». Когда журнал партии переезжает в API, свести к одному правилу (в `packages/core/src/kinds.ts` уже есть `ruNum`) и покрыть тестом на этих числах. В коде шага 1 не менять.
- **Обвязка сквозных тестов** (шаг 6): перезапуск сервиса на том же порту с чистой памятью, как `Service.restart` в `tests/support.py`. `test_streams.py` (поток SSE → цикл событий Python) в Node смысла не имеет — осознанно выброшен.

## Риски

- **«Заново» разрастается.** Снять: контракт API (адреса, тела, `{detail}`, unix-секунды, SG/EBC) сохраняется, интерфейс не переписывается; улучшения — только из таблицы в разделе 4 и `ack` после записи; всё остальное — в `roadmap.md`.
- **Перенос данных с ошибкой.** Снять: `--verify`, тест на дампе, проверка руками на ПК с копией данных, старый том живёт месяц, первые дни без варок.
- **Совместимость входа.** Снять: тест на строках из старой базы; первая проверка после переключения — вход своей учёткой.
- **WebSocket за nginx, sharp на alpine, `web-push` с тем же ключом** — всё стандартное, но проверить на шагах 6–8 до переключения (у `web-push` ключ VAPID — те же 32 байта P-256 base64url; при несовпадении браузеры переподпишутся сами, это штатно).
- **Память на сервере после переключения.** Снять: `mem_limit` у контейнеров и замер `docker stats` в первые дни.
- **Долго без новых функций** (~6–9 недель календаря). Снять: шаги независимы по разделам, можно прерываться; функция в очереди — делается уже в новом стеке на своём шаге.
